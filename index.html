🌟 ภาพรวม: Microsoft SLA คืออะไร🌟 Overview: What is a Microsoft SLA?

Service Level Agreement (SLA) คือสัญญาที่ Microsoft ให้ไว้กับลูกค้าเกี่ยวกับ uptime และ connectivity ของ Online Services ต่าง ๆ เช่น Azure, Microsoft 365, Dynamics 365 และ Intune

SLA ครอบคลุมบริการ: Azure  |  Microsoft 365  |  Dynamics 365  |  Enterprise Mobility Suite

สูตรคำนวณ Monthly Uptime Percentage

# สูตรมาตรฐาน Microsoft
Monthly Uptime % = (Total Billable Minutes − Downtime Minutes) ÷ Total Billable Minutes × 100

# ตัวอย่าง: เดือนมี 43,200 นาที, เกิด Downtime 120 นาที
= (43200 − 120) ÷ 43200 × 100 = 99.72%
⚠️
ข้อควรทราบ: SLA วัดตาม definition ของ Microsoft ไม่ใช่ตาม perception ของลูกค้า เวลา Maintenance ที่นัดไว้ล่วงหน้า, เหตุสุดวิสัย (force majeure), หรือ configuration ของลูกค้าเองที่ไม่ถูกต้อง จะ ไม่นับเป็น Downtime ตาม SLA

ตาราง Service Credit ตามโปรไฟล์ SLA ที่พบบ่อย

🔎 ขั้นตอนที่ 1 — ตรวจจับ Outage🔎 Step 1 — Detect the Outage

เปิด Service Health Dashboard ไปที่ Microsoft 365 Admin Center → Health → Service Health หรือ Azure Portal → Help + support → Service Health
จดบันทึก Incident ID รหัส Incident จะอยู่ในรูปแบบ EX25194 (ตัวอักษร 2 ตัว + ตัวเลข) ดูตารางรหัสบริการด้านล่าง
อ่าน Post Incident Review (PIR) หลัง Incident ปิด Microsoft จะออก PIR ซึ่งระบุ root cause, timeline และผลกระทบอย่างเป็นทางการ
ℹ️
Advisory Incidents ≠ SLA Credit: Incident ที่ระบุว่า "Advisory" (อาจได้รับผลกระทบ) โดยปกติ ไม่มีสิทธิ์ขอ SLA Credit ต้องเป็น Incident ที่ระบุว่า tenant ของคุณ ได้รับผลกระทบจริง ดูรายละเอียดประเภทใน section ถัดไป

🛡️ ประเภทที่ Service Health แสดง — แบบไหนเคลม SLA ได้🛡️ Service Health Event Types — Which Qualify for SLA Credit

ℹ️
ไม่ใช่ทุกข้อความใน Service Health จะเคลม SLA Credit ได้ ก่อนยื่นต้องแยกให้ออกว่า event นั้นเป็น ประเภทใด (type), มาจากไหน (origin), และอยู่ใน สถานะใด (status) ตารางด้านล่างสรุปตามเอกสาร Microsoft Learn

📦 Microsoft 365 / Dynamics 365 / Intune Admin Center

❗️ Incident

บริการหรือฟังก์ชันหลัก ใช้งานไม่ได้ มีผลกระทบต่อผู้ใช้อย่างชัดเจน (ส่งอีเมลไม่ได้, Sign-in ไม่ได้) Microsoft จะโพสต์อัปเดตต่อเนื่อง และออก PIR หลังปิดเหตุการณ์

เข้าเกณฑ์เคลม SLA ได้ (หาก tenant กระทบและ uptime ต่ำกว่า commitment)

⚠️ Advisory

รับรู้ปัญหาแต่บริการ ยังใช้งานได้ — มักเป็น intermittent, ขอบเขตจำกัด หรือมี workaround

ปกติ “ไม่” เข้าเกณฑ์ — ยื่นได้เฉพาะเมื่อพิสูจน์ user impact จริงพร้อมหลักฐานเชิงปริมาณ

🌎 Issue Origin — ต้นตอของปัญหา

Issue Originคำอธิบายเคลม SLA ได้?
Microsoft Infrastructure ปัญหาเกิดใน cloud infrastructure ของ Microsoft เอง (เช่น Exchange, M365 backend) ✅ ใช่ (ถ้าเป็น Incident + ต่ำกว่า SLA)
Third-party Infrastructure ปัญหาเกิดจาก third-party ที่องค์กร depend (เช่น STS provider ภายนอก throttle) ❌ ไม่ได้ — อยู่นอก Microsoft scope
Customer Infrastructure / "Your org" ปัญหาเกิดในระบบของลูกค้าเอง (เช่น certificate หมดอายุ, STS ของลูกค้า) ❌ ไม่ได้ — ลูกค้าต้องแก้เอง

🔄 Status ของ Incident/Advisory และผลต่อการเคลม

Statusความหมายใช้ประกอบการเคลมได้?

Service degradationยืนยันแล้วว่าบริการช้าหรือมี feature ไม่ทำงาน✅ ใช่
Service interruptionผู้ใช้เข้าใช้งานไม่ได้ กระทบชัดเจน consistent✅ ใช่
Restoring serviceพบสาเหตุและกำลังกู้คืนบริการ✅ ยังอยู่ในช่วง downtime
Extended recoveryกำลังกู้คืนให้ผู้ใช้ส่วนใหญ่ แต่ยังเหลือบางส่วน✅ ใช่
Investigation suspendedMicrosoft ขอข้อมูลเพิ่มจากลูกค้าเพื่อสอบสวนต่อ⚠️ รอข้อมูล
Service restoredยืนยันว่าแก้ไขเสร็จแล้ว✅ ใช้เป็นหลักฐานปิด incident

💼
Planned Maintenance ไม่แสดงใน Service Health
สำหรับ M365 การบำรุงรักษาที่นัดหมายล่วงหน้าจะอยู่ใน Message Center ภายใต้หมวด “Plan for change” ช่วงเวลานี้ ไม่นับเป็น downtime ตาม SLA — เมื่อคำนวณให้หักออกจาก Raw Downtime

☁️ Azure Service Health — 5 ประเภท Event

Event Type เนื้อหา Severity / Tags เคลม SLA ได้?
Service issues Outage หรือ degradation ที่กระทบ resource ของคุณตอนนี้ — unplanned Error (widespread) / Warning (specific) / Informational (management ops) + tags: Action recommended, Preliminary PIR, Final PIR, False positive ✅ ใช่ (Error/Warning)
Planned maintenance การบำรุงรักษาที่นัดล่วงหน้า อาจมี brief downtime Warning (emergency) / Informational (standard) ❌ ไม่ — SLA ยกเว้น
Health advisories การเปลี่ยนแปลงที่ต้องให้ความสนใจ เช่น feature deprecation, retirement, upgrade requirement Warning (prompt action) / Informational ❌ ไม่ — เป็นคำแนะนำ
Security advisories การแจ้งเตือนด้าน security ที่อาจกระทบ availability Warning / Informational ❌ ไม่ — การแจ้งเตือน
Billing updates การสื่อสารเกี่ยวกับ subscription/billing Informational ❌ ไม่เกี่ยวกับ SLA
🔎
ดูประเภทจาก Azure Resource Graph: ในตาราง ServiceHealthResources field properties.EventType จะแสดงค่าเช่น ServiceIssue, PlannedMaintenance, HealthAdvisory, SecurityAdvisory และ properties.Status จะเป็น Active หรือ Resolved ช่วยยืนยันประเภทก่อนยื่นเคลม

สัญญาณที่พบผลประเมินเหตุผล
M365 Incident + Issue origin = Microsoft + Status = Service interruption/degradation ✅ เคลมได้ (ถ้า uptime < SLA) Core case — ตรงตามนิยาม Downtime
Azure Service issue severity Error หรือ Warning + Impact start/mitigation time ชัดเจน ✅ เคลมได้ (ถ้า uptime < SLA) มี timestamp ครบสำหรับคำนวณ Monthly Uptime %
M365 Advisory + ไม่มีหลักฐาน user impact ❌ ไม่ได้ Advisory ปกติไม่เข้าเกณฑ์ — ต้องพิสูจน์ impact ด้วย logs/retry
Issue origin = Customer หรือ Third-party ❌ ไม่ได้ SLA ยกเว้น customer-side และ third-party dependency
Azure Planned maintenance ❌ ไม่ได้ SLA exclusion — ต้องหักออกจาก Downtime ถ้ามีการใช้ร่วม
Status = False positive ❌ ไม่ได้ Microsoft ยืนยันว่าไม่ได้มี outage จริง
Azure Health/Security advisory หรือ Billing update ❌ ไม่ได้ ไม่ใช่ outage; เป็นการแจ้งเตือนหรือเรื่อง billing
Service issue ที่ยังไม่มี PIR และ Microsoft ขอข้อมูลเพิ่ม (Investigation suspended) ⚠️ รอ รวบรวมหลักฐานส่งกลับ แล้วรอ status เปลี่ยนเป็น Service restored + PIR ก่อนยื่น

📊 ขั้นตอนที่ 2 — ประเมิน SLA (5-Pass Method)📊 Step 2 — Evaluate SLA (5-Pass Method)

🔐 Pass 1: Definitions

อ่านนิยามของ Downtime, Valid Request, Total Billable Minutes ในเอกสาร SLA ก่อนเสมอ — นิยามเหล่านี้กำหนดว่าอะไรนับเป็น failure จริง

📈 Pass 2: Measurement

ทำความเข้าใจวิธีคำนวณ — time-based vs. request-based, retry requirement, และ aggregation scope (per instance หรือ across subscription)

❌ Pass 3: Exclusions

ระบุเงื่อนไขที่ ไม่ครอบคลุม: planned maintenance, force majeure, customer misconfiguration, exceeded quota, preview features

💡 Pass 4: Design Signals

ใช้ SLA เป็น input สำหรับ architecture — เช่น ถ้า SLA ต้องการ retry logic ให้ implement ก่อน ไม่เช่นนั้น failure จะไม่นับใน SLA

📋 Pass 5: ตรวจสอบว่า Incident ละเมิด SLA หรือไม่

คำนวณ Monthly Uptime % จากข้อมูลจริง ใช้สูตร: (Total Billable Min − Downtime Min) ÷ Total Billable Min × 100
หักเวลาที่ไม่นับ ลบ planned maintenance, excluded events, และช่วงที่ configuration ไม่ตรงตาม prerequisite
เปรียบเทียบกับ SLA Threshold ถ้าตัวเลขต่ำกว่า committed % (เช่น 99.9%) คุณมีสิทธิ์ยื่นขอ Credit

📄 ขั้นตอนที่ 3 — รวบรวมหลักฐาน📄 Step 3 — Collect Evidence

Microsoft แบ่งหลักฐานเป็น 2 ชุด — Required Information (ข้อมูลพื้นฐานบังคับทุกเคส) และ Evidence of Customer Impact (หลักฐานพิสูจน์ผลกระทบจริง) ต้องมีครบทั้ง 2 ชุดก่อนยื่น มิฉะนั้น Microsoft จะปฏิเสธหรือทวงหลักฐานเพิ่ม

🔒 ชุดที่ 1 — Required Information

ข้อมูลพื้นฐานที่ Microsoft กำหนดให้ระบุในทุก credit request

  • Customer Tenant GUID — ID ของ tenant ที่ได้รับผลกระทบ
  • Outage Incident Identifier — เช่น EX25194 จาก Service Health Dashboard
  • หลักฐานว่าลูกค้า ได้รับผลกระทบ และ ขอ Credit
  • ระบุว่า subscription ซื้อผ่าน CSP หรือไม่ (Yes/No)
🔍 ชุดที่ 2 — Evidence of Customer Impact

หลักฐานเชิงเทคนิค/ธุรกิจที่พิสูจน์ว่าเกิดผลกระทบจริง

  • Time & duration — timestamps เริ่ม/สิ้นสุด Incident พร้อม timezone
  • จำนวนและที่ตั้ง ของ users ที่ได้รับผลกระทบ
  • Error details — error codes, error messages, timeout behaviors
  • Request / retry logs — หลักฐานว่าทำ retry หาก SLA กำหนด
  • Troubleshooting ที่ทำระหว่างเกิดเหตุ (failover, workaround)
  • Email จากลูกค้า — ส่งจาก domain ของ tenant ที่กระทบ (ไม่รับ personal email)
  • Support ticket number และบันทึก contact กับลูกค้า (ถ้ามี)
❌
ข้อมูลต่อไปนี้ "ไม่เพียงพอ" สำหรับการ process:
ชื่อลูกค้า + Tenant ID + Partner Ticket Number + Ticket created timestamp เพียงเท่านี้ — Microsoft จะ reject หรือทวงหลักฐานเพิ่ม ทำให้ ticket ค้างนานและอาจเลย deadline

ซื้อผ่าน Partner ไทย/ต่างประเทศ ใบเสร็จออกโดย Partner มีคำว่า CSP / Cloud Solution Provider บน invoiceCSP
มี Enrollment Number จาก Microsoft; เข้าใช้ EA portal (ea.azure.com เดิม) หรือ Billing scope เป็น Enterprise Agreement; มีสัญญา EA/EAS/SCE 3 ปีEA (Enterprise Agreement)
ไม่แน่ใจ: ตรวจที่ Azure Portal → Cost Management + Billing → Billing scopes ดู Account typeตรวจซ้ำก่อนยื่น

💻 Direct (Web Direct / MCA)

ลูกค้าซื้อตรงจาก Microsoft ผ่าน portal ทั่วไป ใช้ Microsoft Customer Agreement (MCA) เป็นหลัก ยื่นเองได้โดยไม่ต้องผ่าน partner

ผู้ยื่น

  • Global Admin / Billing Admin ของ tenant
  • หรือ Service Support Admin (M365)
  • Azure: Billing account owner / contributor

เส้นทาง

Azure: portal.azure.com → Help + Support → New support request → Issue type: Billing → Problem type: Refund request → ระบุ SLA credit + วัน/เวลา/service
M365/Dynamics: admin.microsoft.com → Support → New service request → Billing → ขอ SLA Service Credit
แนบ Incident ID, PIR, timestamps, impact evidence
ติดตามผ่าน portal เดียวกัน

รูปแบบ Credit

หักออกจาก invoice ถัดไป หรือสำหรับ MCA แสดงเป็น credit memo ใน Billing → Invoices

Deadline

Azure: 2 เดือน · M365/อื่น ๆ: 1 เดือน (นับจากสิ้น billing month)

🤝 CSP (Cloud Solution Provider)

ลูกค้าซื้อผ่าน Partner — Partner เป็นผู้ยื่นแทนลูกค้า (ลูกค้าปลายทางยื่นเองผ่าน Partner Center ไม่ได้)

ผู้ยื่น

  • CSP Direct Provider หรือ Indirect Provider
  • Role: Admin agent + GDAP relationship กับลูกค้า
  • ❌ Indirect Reseller ยื่นไม่ได้ ต้องส่งต่อให้ Indirect Provider

เส้นทาง

M365/Dynamics: Partner Center → Help + support → Create request → Cancel, Credit or suspend (non-Azure) subscriptions
Azure: Partner Center → Administer customer → Azure Portal (context ลูกค้า) → New support request → Billing → Refund Request
แนบ Required Information + Evidence (ดูรายละเอียดใน section รวบรวมหลักฐาน)
Partner ออก credit note ให้ลูกค้าต่อหลังได้รับอนุมัติ

รูปแบบ Credit

ปรากฏใน invoice + Reconciliation file ที่ Partner Center → Billing → Invoices & reconciliation → Partner ส่งต่อให้ลูกค้าเอง

Deadline

เหมือน Direct: Azure 2 เดือน · อื่น ๆ 1 เดือน ครอบคลุมทั้ง legacy และ NCE

🏢 EA — Enterprise Agreement (รวม EAS, SCE)

ลูกค้าองค์กรขนาดใหญ่ที่เซ็นสัญญา EA 3 ปีกับ Microsoft (ซื้อผ่าน LSP/SSP partner หรือ EA Direct) มี Enrollment Number และ Enterprise Administrator role ต่างจาก Direct/CSP เพราะ SLA credit จะใช้เป็น credit สำหรับใช้งาน Azure ในอนาคต ไม่ใช่ cash refund และ หมดอายุเมื่อครบ enrollment anniversary term

ผู้ยื่น

  • Enterprise Administrator (EA Direct)
  • Account Owner ของ subscription
  • EA Indirect: ติดต่อ Partner Administrator ของ LSP/SSP ที่เป็นตัวแทนของ enrollment — ลูกค้ายื่นเองไม่ได้
  • Microsoft Account Team / Account Manager สำหรับเคสที่ซับซ้อน

เส้นทาง — Technical SLA credit

เข้า Azure Portal ด้วย Enterprise Admin
Help + Support → New support request → Issue type: Billing → Problem type: Refund request
ระบุ Enrollment Number, Incident ID, Impact window
EA Indirect: แจ้ง LSP/SSP ให้ยื่นแทนผ่าน VL Central → My Cases & Support หรือ Microsoft Account Team

รูปแบบ Credit ที่แตกต่าง

  • Service Credit ≠ cash refund — เป็นเครดิตใช้กับ Azure consumption ในอนาคตเท่านั้น
  • Expire เมื่อจบ enrollment anniversary term ปัจจุบัน (ใช้ไม่ทัน = หายไป)
  • ปรากฏในรายงาน usage summary ด้วย Accounting Code O21 — Service Level Agreement Credit
  • ตรวจที่ Azure Portal → Cost Management + Billing → Billing scope (EA enrollment) → Usage + charges

Deadline

Azure: ภายใน 2 เดือนจากสิ้น billing month · เตือนเป็นพิเศษให้ยื่นเร็ว เพื่อให้มีเวลาใช้ credit ก่อน anniversary term หมด

เครื่องมือเพิ่มเติม

  • VL Central → Credits and transfers workspace (ใช้กับ licensing credits ไม่ใช่ SLA technical แต่สำคัญสำหรับ volume license ปัญหาอื่น)
  • VL Central → My Cases & Support สำหรับ escalation

Pitfalls ที่พบบ่อย:
• CSP Indirect Reseller ยื่นเอง → ถูก reject (ต้องให้ Indirect Provider ยื่น)
• EA Indirect ลูกค้ายื่นเองใน Azure Portal → เคสถูกส่งกลับให้ติดต่อ LSP/SSP
• EA ยื่นช้าจน credit หมดอายุก่อนได้ใช้ (anniversary term ครบ)
• Direct ใช้ personal email แนบเป็น evidence → ถูก reject ต้องเป็น email จาก tenant domain
• ใช้ Advisory incident เป็นหลักฐานหลัก → ปกติไม่เข้าเกณฑ์

☁️ Microsoft Azure

Sign in ที่ Azure Portal ด้วย account ที่ได้รับผลกระทบ
ไปที่ Help + Support → New Support Request
เลือก Issue type: Billing → Problem type: Refund Request
ระบุว่าขอ SLA credit พร้อม วันที่/เวลา/timezone และ impacted services
ตรวจสอบ contact details → Create

💼 Microsoft 365 / Dynamics 365 / Intune — CSP Partner

เส้นทางละเอียดจาก Partner Center (10 ขั้น) — ใช้เมื่อ Partner ยื่น Service Credit Request แทนลูกค้า CSP Direct/Indirect Provider เท่านั้น (Indirect Reseller ยื่นเองไม่ได้)

ยืนยัน Role และ GDAP ผู้ยื่นต้องมี Admin agent role ใน Partner Center และ GDAP relationship ที่ active กับ tenant ลูกค้าโดยมี role Service support administrator เป็นอย่างน้อย (มี permission Microsoft.office365.supportTickets/allEntities/allTasks)
ตรวจ Service Health ของลูกค้า Sign in partner.microsoft.com/dashboard → Customers → เลือก customer → Service management → ดู Service health เพื่อยืนยัน Incident ID และ status (ต้องไม่ใช่ Advisory อย่างเดียว)
เปิดเส้นทางสร้าง Service Request มี 2 วิธี:
(ก) Customer List → เลือกลูกค้า → Service request → New Request
(ข) เมนู CSP → Administer → Service Requests → New request
เลือก workload ที่ได้รับผลกระทบ เช่น Exchange Online, SharePoint Online, Microsoft Teams, Dynamics 365, Intune, EMS — Partner Center จะเปิด workload portal (เช่น M365 Admin Center) ใน context ของ partner สำหรับ tenant ลูกค้า
ลิงก์ Support Plan (ถ้าจำเป็น) สำหรับบางบริการให้ผูก support contract/entitlement หมายเหตุ: M365 Admin Center ไม่รองรับการผูก support plan ด้วย Access ID/Contract ID (ใช้สิทธิ์ CSP program entitlement โดยอัตโนมัติ)
เลือก Support Category: SLA Credit ใน workload portal เลือกหมวดสำหรับ billing / credit (เช่น Billing → Cancel, Credit or suspend subscriptions หรือ equivalent) หรือข้ามไปยัง Partner Center Create Request (non-Azure) โดยตรงก็ได้
กรอกฟอร์ม Ticket Title ชัดเจน เช่น SLA Service Credit Request — EX25194 — Exchange Online Description ระบุ: Tenant GUID, Incident ID, Impact window (UTC + timezone), จำนวน users ที่กระทบ, อาการและ error, และสิ่งที่พิสูจน์ว่าเป็น Microsoft infrastructure (ไม่ใช่ customer/third-party)
แนบหลักฐาน 2 ชุด Required: Tenant GUID, Incident ID, CSP flag (Yes), อีเมลจากลูกค้าในโดเมน tenant ที่ขอ credit
Evidence of impact: Service Health screenshot / PIR, error logs + request IDs, retry logs, troubleshooting ที่ทำ, support contact log
Contact: ใช้ข้อมูลของ Partner ใน Contact information ต้องใส่ชื่อ/อีเมลของ Partner เท่านั้น ห้ามใส่ของลูกค้า (เพื่อให้ Microsoft ตอบกลับผ่าน Partner) → กด Submit → รับ Case/Ticket Number เก็บไว้
ติดตามและรับ Credit ดูสถานะที่ Partner Center → Service requests หรือ M365 Admin Center → Support → See all support tickets หลังอนุมัติ Credit จะปรากฏใน Partner Invoice + Reconciliation File (Partner Center → Billing → Invoices & reconciliation) ให้ Partner ออก Credit Note ให้ลูกค้าต่อ
⚠️
ข้อควรระวัง: CSP Partners ไม่สามารถสร้าง support request แทน partner อื่น ๆ ได้ (อาจทำให้ ticket ล่าช้า) และหากซื้อผ่าน Indirect Reseller ต้องส่งต่อให้ Indirect Provider เป็นผู้ยื่นใน Partner Center
✅
Credit จะครอบคลุมเฉพาะ service ที่ได้รับผลกระทบจริง: เช่น ถ้า M365 Suite เจอปัญหาแค่ SharePoint — credit จะได้เฉพาะ SharePoint ไม่ใช่ทั้ง suite และ credit ไม่ครอบคลุม lost revenue หรือ reputational damage
